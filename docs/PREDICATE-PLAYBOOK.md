# 判据选用手册（开发经验沉淀）

> 这些是用真实误报换来的经验。写规则前先读一遍，能省掉大半返工。

## 一、先定对象，再选判据

1. 每条规则必须先回答：**审计对象是什么**——命令 / 文件写入 / 轮次 / 会话 / 记录文档
2. 对象要用 `pathPattern` + `excludePath` 收窄；不收窄就会命中 `AGENTS.md`、`README.md` 这类无关文件
3. 基数应当是「事件数」而非「全部文件数」：例如“记录五必录”的分母是**记录文件**，不是所有 .md

## 二、正则是最容易出事的一类

1. **不要用宽泛正则**：`来源|sources` 曾导致 195/195 全命中，全部误报
2. 匹配命令要**段首锚定**：`(?:^|[;&|]\s*)sudo\b`，不要裸写 `sudo`
3. 加上**引号感知**：`python3 -c "…sudo…"` 里的字样不算命令
4. JS 不支持 `(?s)`，需要跨行用 `[\s\S]`

## 三、能靠平台事实就别靠猜

1. "有没有审批"看 `approval/asked` + `approval/decided`，不要靠命令文本猜
2. "是不是子会话"看 `sandbox/mode.source === 'delegation'`
3. "后台跑了没"看 `job/registered` 与 `job/settled`
4. "长任务"用 `turn/start` 与 `turn/end` 的跨度，或调用次数
5. 红线类优先用 `approval-gated`，而不是 `regex`

## 四、语义规则不要硬编判据

1. “拿不准先问”“指不到证据不写结论”这类无法机械判定
2. 正确做法：保留为提示规则（状态永远 unknown），或让模型复核给出参考
3. 硬编判据只会产生假结论，比不判更糟

## 五、误报是长期成本

1. 发现要能标误报，且标记后从命中里扣减
2. 变化要与基线比较，`|z|<1.96` 说明无明显变化，不该飘红
3. 噪声大的规则降级为 `stat`，只统计不飘红

## 六、规则写了要有成本意识

1. 每条规则都会进提示词，长了就是成本，也会稀释注意力
2. 红线优先、硬约束次之、软规则最后；超过 20 条的规则集要开始考虑合并
3. 定期跑「规则体检」：重复、冲突、无判据、超长
